# 2차 설계 — 평행 우주(친구) 독서 기록 앱

- 작성일: 2026-11-12
- 확정: 책 데이터 = **YES24 Open API**, 멀티버스 = **B안 평행 우주(친구)**
- 확정(11-12): Next.js 16.4.5 + MongoDB, 모바일 웹(PWA) → 안드로이드는 TWA로 플레이스토어
- 진행: Phase 0 완료(YES24 키 실측만 남음) — 실행 방법·구조는 루트 CLAUDE.md

---

## 1. 컨셉

> **11-12 바뀜 — 나만의 책장** (사용자 원래 구상): 높이(cm)를 쌓는 대신, 내 책장에서 책을 꺼내 읽고(타이머) 덮을 때 "오늘 몇 쪽까지"를 남기고 다시 꽂는다. 쌓인 기록으로 나만의 읽는 속도·한 권 읽는 시간. 멀티버스 = 책장마다 하나의 우주, 같은 책이 꽂힌 책장끼리 통로. 아래 '내 우주 높이·책등 탑' 부분은 지난 안이다 — 지금 구조는 루트 CLAUDE.md.

> (지난 안) 내가 읽은 책으로 내 우주를 쌓고, 친구와 같은 책을 읽으면 두 우주 사이에 통로가 열린다.

- **혼자 써도 되는 것**: 기록 → 내 우주에 책등이 쌓임(높이 cm 목표). 북적북적에서 검증된 루프
- **친구가 있으면 생기는 것**: 통로 → 방문 → 담아 오기·발도장. 북적북적에 없는 것(리뷰 요청 1순위)
- 쌓기라는 구조는 참고하되, 북적북적의 이름·'북적이' 캐릭터·화면 구성을 닮게 만들지 않는다

## 2. 핵심 규칙

### 2-1. 내 우주
- 우주 높이 = **'읽은' 책 두께의 합** (북적북적과 같은 기준). '읽는 중'인 책은 탑 위에 반투명으로 얹되 높이에는 넣지 않음
- 두께 결정 순서 (`thicknessSource`로 출처 기록)
  1. YES24 `detail=Y`의 크기 필드(width/height/length 중 두께 — 키 받아 실측으로 확정)
  2. 없으면 추정: 쪽수 × 0.05mm + 표지 2mm (300쪽 ≈ 1.7cm)
  3. 사용자가 직접 고침
- 책등 이미지 = YES24 `sideCover`. 이미지가 없어도 대체 이미지 URL이 와서 응답만으로는 구분 불가 → 처음엔 그대로 쓰고, 대체 이미지 판별은 실측 후 결정
- 목표 높이: 기본 100cm, 사용자가 바꿀 수 있음

### 2-2. 통로 (Portal)
- **조건**: 나와 친구의 서재에 '같은 책'이 있으면 통로
- **같은 책 판정**
  1. `isbn13` 일치 → 같은 판본 (작은 배지)
  2. `workKey` 일치 → 판본이 달라도 같은 책 (리커버·큰글자·개정판)
     - `workKey = 정규화(제목) + "|" + 정규화(첫 저자)`
     - 정규화: 괄호·대괄호 안 판본 표기 제거 → 부제(`:`, ` - ` 뒤) 제거 → 공백·문장부호 제거 → 소문자
- **상태**
  | 상태 | 조건 | 보이는 모습 |
  |---|---|---|
  | 열린 통로 | 둘 다 '읽은' | 밝게, 지나갈 수 있음 |
  | 희미한 통로 | 한쪽만 '읽은', 다른 쪽은 '읽는 중'·'읽고 싶은' | 흐리게 + "완독하면 통로가 열려요" |
  | 없음 | 어느 한쪽이 '중단한' | — |
- **통로 굵기** = 두 사람 사이 열린 통로 개수 → 멀티버스 지도의 선 굵기
- **이벤트**: 열린 통로가 새로 생기면 두 사람에게 알림 — "지민님과 『데미안』으로 통로가 열렸어요"

### 2-3. 방문
- 친구 우주는 **읽기 전용**
- 볼 수 있는 것(기본): 탑, 책 목록·상태, 별점, 한줄평. 메모는 본인이 '공개'로 바꾼 것만
- 할 수 있는 것
  - **담아 오기**: 친구 책을 내 '읽고 싶은'에 추가 (`addedFrom`에 친구 기록)
  - **발도장**: 친구 책에 반응 하나 남기기
- 방문하면 상대에게 "현우님이 다녀갔어요" (같은 사람은 하루 한 번으로 묶음)

### 2-4. 친구
- 초대 링크·코드 → 링크를 연 사람이 '친구 되기'를 누르면 바로 친구 (초대한 쪽은 이미 동의한 것으로 봄)
- 친구 끊기 가능 → 끊으면 통로·방문 기록 숨김
- 우주 공개 범위: 친구만(기본) / 나만

### 2-5. 초대받은 사람의 첫 화면 (콜드 스타트 해결)
- 초대 링크를 열면 **가입 전에도 초대한 사람의 우주를 미리 봄**
- 가입 직후 첫 화면 = **"지민님 서재에서 나도 읽은 책 고르기"** → 고른 만큼 내 서재가 채워지고 통로가 바로 열림
- 효과: 새 사용자의 빈 서재 문제와 친구 기능의 빈 지도 문제를 한 번에 해결

[앱 첫 실행] ─────────────────────────→ [로그인] ─────────────────────────────────────┤
                                                                                     ▼
                                                                          ┌── [내 우주(홈)] ──┐
                                                                          │                   │
             [책 추가] ←── + 버튼 ─────────────────────────────────────────┤                   │
               ├ 검색(YES24)                                               │                   │
               ├ 바코드(ISBN)                                              │                   │
               └ 직접 입력                                                 │                   │
                    ↓                                                     │                   │
               [상태 고르기] → 탑에 한 권 쌓임 ─────────────────────────────┘                   │
                                                                                              │
[서재] 리스트 / 캘린더 / 통계(장르) ── 책 탭 ──→ [책 상세] ──→ "이 책으로 통하는 우주 2곳"      │
                                                                     ↓                        │
[멀티버스 지도] ── 친구 우주 탭 ──→ [친구 우주 방문] ── 통로 책 탭 ──→ [통로 상세]             │

### 멀티버스 지도 (와이어)
```
              (지민의 우주 42cm)
                    ║ 통로 3
 (서연 18cm) ── (내 우주 63cm) ══════ (현우 120cm)
        통로 1          ║ 통로 2        통로 7
                (엄마 30cm)
```
- 선 굵기 = 열린 통로 수, 점선 = 희미한 통로만 있음
- 친구가 많으면 통로 굵은 순으로 12명까지 원형 배치 + 나머지는 목록

## 4. 데이터 구조 (MongoDB)

> YES24 약관상 '체계적 DB 축적 금지' → 전역 책 카탈로그를 만들지 않는다. 책 정보는 **사용자 기록(userBooks)에 기록용 최소 필드만** 담고, 소개·가격·별점은 실시간 조회 + 24시간 캐시.

### users
| 필드 | 타입 | 설명 |
|---|---|---|
| `_id` | ObjectId | |
| `nickname` | string | 표시 이름 |
| `handle` | string (unique) | 초대·검색용 아이디 |
| `avatarUrl` | string? | |
| `universeName` | string | 예: "지민의 우주" (바꿀 수 있음) |
| `goalCm` | number | 기본 100 |
| `visibility` | `friends` \| `private` | 기본 friends |
| `auth` | `{provider, providerId}[]` | 카카오·구글 등 |
| `createdAt` | Date | |

### userBooks — 내 서재의 책 한 권
| 필드 | 타입 | 설명 |
|---|---|---|
| `_id`, `userId` | ObjectId | |
| `isbn13` | string? | **반드시 저장** — 출처가 바뀌어도 다시 찾는 열쇠 |
| `workKey` | string | 판본 무관 같은 책 판정 키 |
| `yes24ItemId` | number? | 상품 링크용 |
| `title`, `author`, `publisher` | string | 기록용 최소 필드 |
| `pages` | number? | |
| `thicknessMm` | number | 탑 높이 계산 |
| `thicknessSource` | `yes24` \| `estimate` \| `user` | |
| `coverUrl`, `sideCoverUrl` | string? | YES24 URL 그대로 사용 |
| `category` | string? | `goodsSortNm` (장르 통계) |
| `status` | `want` \| `reading` \| `read` \| `stopped` | |
| `rating` | number? | 0.5 단위 |
| `oneLiner` | string? | 한줄평 |
| `startedAt`, `finishedAt` | Date? | 캘린더 |
| `addedFrom` | `{type: search\|barcode\|manual\|friend, friendId?}` | |
| `createdAt`, `updatedAt` | Date | |

인덱스: `{userId, status}`, `{workKey, userId}`, `{userId, isbn13}`

### memos
`_id, userId, userBookId, text, page?, isPublic(기본 false), createdAt` — 인덱스 `{userBookId, createdAt}`

### friendships
`_id, a, b, createdAt` — 두 사용자 id 를 `a < b` 로 정렬해 저장, 인덱스 `{a, b}` unique + `{b}`
(배열 `pair` 에 unique 를 걸면 Mongo 가 원소마다 unique 로 봐서 친구를 한 명밖에 못 맺는다 — 11-12 Phase 0 에서 발견해 바꿈)

### invites
`_id, code(unique), inviterId, createdAt, expiresAt` — 링크 `/i/{code}`

### visits
`_id, visitorId, hostId, viaWorkKey?, createdAt` — 인덱스 `{hostId, createdAt}`

### stamps (발도장)
`_id, fromUserId, toUserId, userBookId, kind, createdAt` — 인덱스 `{userBookId}`

### notifications
`_id, userId, type: portal_opened|visited|stamped|friend_joined, payload, readAt?, createdAt` — 인덱스 `{userId, createdAt}`

### apiCache — YES24 응답 일시 캐시
`_id(키: 검색어·ISBN), body, createdAt` — **TTL 인덱스 24시간**

### 통로 계산
- 저장하지 않고 조회할 때 계산: 나 + 친구들의 userBooks를 `workKey`로 묶어 두 명 이상 겹치는 것만
- `userBooks.status`가 바뀔 때 해당 `workKey`만 다시 계산 → 새 열린 통로가 생기면 `notifications` 2건

## 6. YES24 사용 방식

- **호출 시점**: 검색은 입력이 끝나고 검색 버튼·엔터에서만(글자마다 호출 안 함), 상세는 책을 고를 때 한 번
- **한도 계산**: 책 등록 1건 ≈ 검색 1~2회 + 상세 1회 = 약 3회 → Basic 일 2만 회로 하루 약 6천 건 등록. 넘으면 Partner(일 10만, 1:1 문의)
- **표기**: YES24 데이터가 보이는 화면 하단에 "도서 정보·이미지 제공 YES24", 책 상세·통로 상세에 "YES24에서 보기"(애드온 신청 시 `addOnLink`)
- **키**: `.env`의 `YES24_API_KEY`, 서버에서만 호출. 계정당 키 1개·다른 서비스와 공유 금지 → **이 앱 전용 계정**(가능하면 법인 회원)으로 발급
- **바코드**: 안드로이드 크롬 기본 바코드 인식 → 안 되는 기기는 zxing 계열 라이브러리. EAN-13(978·979로 시작)만 ISBN으로 받음

### YES24 1:1 문의로 확인할 것
1. 사용자 독서 기록에 제목·저자·쪽수·표지 URL을 저장하는 것이 '일시 캐싱' 허용 범위인지
2. `detail=Y`의 width/height/length 중 두께는 어느 필드인지
3. 호출 한도가 계정 단위인지 키 단위인지 (문서끼리 다름)
